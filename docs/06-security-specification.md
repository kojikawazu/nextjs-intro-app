## 1. 認証・認可

### 1.1 方針

本プロジェクトはソフトウェアエンジニアの公開ポートフォリオサイトであり、ユーザー認証・認可機能は実装しない。

### 1.2 理由

| 観点 | 説明 |
|------|------|
| サイト特性 | 全コンテンツが一般公開を前提とした情報であり、閲覧制限が不要 |
| ユーザーアカウント | 訪問者にアカウント作成・ログインを求めるユースケースが存在しない |
| データ更新 | ポートフォリオデータはGCS上のJSONファイルで管理され、サイト経由での更新機能を持たない |
| コンタクトフォーム | 匿名での問い合わせを許可する仕様であり、認証を前提としない |

### 1.3 管理者アクセス

- ポートフォリオデータの更新はGCSへの直接操作 (GCSコンソール、gsutil等) によって行う
- GCSへのアクセスはGoogle Cloud IAMにより制御される
- サイト自体に管理画面やCMSは存在しない

## 2. 入力バリデーション

### 2.1 バリデーション戦略

コンタクトフォームにおいて、クライアントサイドとサーバーサイドの二重バリデーションを実装する。クライアントサイドバリデーションはUX向上を目的とし、サーバーサイドバリデーションをセキュリティ上の最終防衛線として位置づける。

### 2.2 クライアントサイドバリデーション

**実装ファイル**: `src/schemas/contact.ts`（クライアント・サーバー共通）
**使用ライブラリ**: Zod + React Hook Form (`@hookform/resolvers/zod`)

| フィールド | ルール | エラーメッセージ |
|-----------|--------|----------------|
| name | 必須、2文字以上、50文字以下 | `お名前は必須です` / `お名前は2文字以上で入力してください` / `お名前は50文字以内で入力してください` |
| email | 必須、メールアドレス形式、255文字以下 | `メールアドレスは必須です` / `正しいメールアドレスを入力してください` / `メールアドレスは255文字以内で入力してください` |
| message | 必須、10文字以上、2000文字以下 | `お問い合わせ内容は必須です` / `お問い合わせ内容は10文字以上で入力してください` / `お問い合わせ内容は2000文字以内で入力してください` |

Zodスキーマ定義:

```typescript
export const ContactFormSchema = z.object({
    name: z.string().min(1).min(2).max(50),
    email: z.string().min(1).email().max(255),
    message: z.string().min(1).min(10).max(2000),
});
```

### 2.3 サーバーサイドバリデーション

**実装ファイル**: `src/app/api/contact/route.ts`

| チェック項目 | ルール | HTTPステータス |
|-------------|--------|---------------|
| 必須チェック | `name`, `email`, `message` が全て存在すること | 400 |
| メール形式 | `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` に一致すること | 400 |
| メッセージ長 | 5000文字以下であること | 400 |

### 2.4 バリデーションの差分

クライアントサイドとサーバーサイドでバリデーションルールに差分が存在する。

| フィールド | クライアント | サーバー | 備考 |
|-----------|-----------|---------|------|
| name 最小文字数 | 2文字 | チェックなし (存在チェックのみ) | サーバー側は緩い |
| name 最大文字数 | 50文字 | チェックなし | サーバー側は未制限 |
| email 最大文字数 | 255文字 | チェックなし | サーバー側は未制限 |
| message 最小文字数 | 10文字 | チェックなし | サーバー側は緩い |
| message 最大文字数 | 2000文字 | 5000文字 | サーバー側の方が緩い |

**推奨事項**: サーバーサイドバリデーションにもZodスキーマを共有利用し、クライアントサイドと同一のルールを適用することを推奨する。

## 3. 環境変数管理

### 3.1 環境変数一覧

| 変数名 | 用途 | 公開範囲 | 必須 |
|--------|------|---------|------|
| `SITE_URL` | サイトの公開 URL（メタデータ / canonical / sitemap / robots の基準） | サーバーサイドのみ。`NEXT_PUBLIC_` は付けない（付けるとビルド時に値が焼き込まれ、Cloud Run の実行時環境変数で上書きできなくなる） | 任意（未設定時は `src/lib/site-url.ts` の正規オリジンにフォールバック） |
| `GCS_PRIVATE_BUCKET_NAME` | GCSバケット名 | サーバーサイドのみ | 必須 (本番) |
| `GCS_JSON_PATH` | GCS上のJSONファイルパス | サーバーサイドのみ | 必須 (本番) |
| `GOOGLE_APPLICATION_CREDENTIALS` | GCSサービスアカウントキーファイルパス | サーバーサイドのみ | 開発環境用 |
| `GOOGLE_CLOUD_PROJECT_ID` | GCPプロジェクトID | サーバーサイドのみ | 開発環境用（`GOOGLE_APPLICATION_CREDENTIALS` と併用） |
| `GOOGLE_CLOUD_PRIVATE_KEY` | GCPサービスアカウント秘密鍵 | サーバーサイドのみ | 実質未使用（`gcs.ts` の `else if` 分岐は `NODE_ENV` が `production`/`development` 以外の場合のみ到達するデッドコード） |
| `GOOGLE_CLOUD_CLIENT_EMAIL` | GCPサービスアカウントメール | サーバーサイドのみ | 同上（デッドコード分岐） |
| `RESEND_API_KEY` | Resend APIキー | サーバーサイドのみ | 必須（`resend.ts` で検証済み） |
| `RESEND_FROM_EMAIL` | メール送信元アドレス（`noreply@introtechkkplus.com`。Resend でドメイン検証済みであることが前提） | サーバーサイドのみ | 必須（`resend.ts` で検証済み。`.env.example` にも記載済み） |
| `MY_MAIL_ADDRESS` | お問い合わせメール受信先 | サーバーサイドのみ | 必須（`resend.ts` で検証済み） |
| `NODE_ENV` | 実行環境 | サーバーサイドのみ | 自動設定 |
| `NEXT_TELEMETRY_DISABLED` | Next.jsテレメトリ無効化 | サーバーサイドのみ | 任意 |
| `FORCE_GCS` | 開発環境でGCS強制使用 | サーバーサイドのみ | 任意 |

### 3.2 環境変数のセキュリティ対策

| 対策 | 説明 |
|------|------|
| `.env` ファイルの除外 | `.gitignore` により `.env` ファイルがリポジトリに含まれないようにする |
| `.env.example` の提供 | 実際の値を含まないテンプレートファイルのみをリポジトリに含める |
| `NEXT_PUBLIC_` プレフィックス | クライアントに公開する環境変数にのみ `NEXT_PUBLIC_` を付与。機密情報を含む変数にはこのプレフィックスを使用しない |
| Cloud Run 環境変数 | 本番デプロイ時は Cloud Run の環境変数設定、または GitHub Actions Secrets 経由で管理 |

### 3.3 実行時チェック

以下の環境変数はコード内で存在チェックが行われ、未設定の場合はエラーをスローする。

| チェック箇所 | チェック対象 | 動作 |
|-------------|-----------|------|
| `src/repositories/resend.ts` | `RESEND_API_KEY` | 未設定時にエラースロー |
| `src/repositories/resend.ts` | `MY_MAIL_ADDRESS` | 未設定時にエラースロー |
| `src/repositories/resend.ts` | `RESEND_FROM_EMAIL` | 未設定時にエラースロー |
| `src/repositories/resend.ts` | `RESEND_API_KEY` のフォーマット | `re_` プレフィックスで始まらない場合にエラー |

## 4. 外部サービスセキュリティ

### 4.1 Google Cloud Storage (GCS)

#### 認証方式

| 環境 | 条件 (`gcs.ts`) | 認証方式 | 説明 |
|------|-----------------|---------|------|
| 本番環境 (Cloud Run) | `NODE_ENV === 'production'` | Application Default Credentials (ADC) | Cloud Run 上ではサービスアカウントが自動的にアタッチされるため、明示的な認証情報は不要 |
| 開発環境 | `NODE_ENV === 'development'` | サービスアカウントキーファイル | `GOOGLE_APPLICATION_CREDENTIALS` で指定されたキーファイルを使用 |
| その他（デッドコード） | 上記いずれでもない場合 | JSON キー認証 | `GOOGLE_CLOUD_PRIVATE_KEY` / `GOOGLE_CLOUD_CLIENT_EMAIL` を使用する分岐が存在するが、通常運用では到達しない |

#### アクセス制御

- GCSバケットはプライベートバケットとして設定 (`GCS_PRIVATE_BUCKET_NAME`)
- サービスアカウントに対してバケットへの読み取り権限のみを付与することを推奨
- バケット名やファイルパスはサーバーサイドの環境変数で管理し、クライアントサイドには露出しない

#### データフロー

```
クライアント → Next.js API Route (/api/portfolio) → GCS (プライベートバケット)
```

クライアントがGCSに直接アクセスすることはなく、サーバーサイドのAPI Routeを介してデータを取得する。

### 4.2 Resend (メール送信)

#### 認証方式

- `RESEND_API_KEY` による API キー認証
- APIキーはサーバーサイドでのみ使用され、クライアントサイドには露出しない

#### セキュリティチェック

| チェック | 説明 |
|---------|------|
| APIキー存在チェック | `RESEND_API_KEY` が未設定の場合はエラースロー |
| APIキーフォーマット | `re_` プレフィックスによるフォーマット検証 |
| 送信先制限 | メール送信先は `MY_MAIL_ADDRESS` (サイト管理者) に固定 |
| 送信元管理 | 送信元アドレスは `RESEND_FROM_EMAIL` で管理 |

#### データフロー

```
クライアント → Next.js API Route (/api/contact) → Resend API → メール受信
```

クライアントがResend APIに直接アクセスすることはない。

## 5. クライアントサイドセキュリティ

### 5.1 外部リンク保護

全ての外部リンク (`target="_blank"`) に `rel="noopener noreferrer"` を付与。

| 属性 | 効果 |
|------|------|
| `noopener` | リンク先ページが `window.opener` を介して元ページを操作することを防止 |
| `noreferrer` | リンク先にリファラー情報を送信しないことでプライバシーを保護 |

**実装箇所**: `src/components/molecules/SocialLinks.tsx`

### 5.2 Node.jsモジュールのクライアントバンドル除外

`next.config.js` のwebpack設定により、以下のNode.jsモジュールをクライアントサイドバンドルから除外。

| 除外モジュール | 除外理由 |
|--------------|---------|
| `fs` | ファイルシステムアクセス防止 |
| `net` | ネットワークソケット操作防止 |
| `tls` | TLS/SSL操作防止 |
| `crypto` | 暗号化モジュールの不要な露出防止 |
| `stream` | ストリーム操作防止 |
| `url` | URL解析モジュールの不要な露出防止 |
| `zlib` | 圧縮ライブラリの不要な露出防止 |
| `http` / `https` | HTTPモジュールの不要な露出防止 |
| `assert` | アサーションモジュールの不要な露出防止 |
| `os` | OS情報アクセス防止 |
| `path` | ファイルパス操作防止 |
| `child_process` | 子プロセス生成防止 |

この設定は、`@google-cloud/storage` や `resend` などのサーバーサイド専用ライブラリが間接的に参照するNode.jsモジュールが、クライアントバンドルに含まれることを防止するために必要である。

### 5.3 エラーメッセージの制御

| 環境 | エラーメッセージ（レスポンス） | 詳細ログ（サーバー） |
|------|--------------|---------|
| 本番環境 | ユーザー向けの汎用メッセージのみ | **出力する**（`logError`。スタックトレース付き） |
| 開発環境 | ユーザー向けの汎用メッセージのみ | 出力する（加えて `logDebug` で進行状況） |

レスポンスには環境を問わず汎用メッセージのみを返し、原因はサーバーログにのみ残す。出力方針は `src/lib/logger.ts` に集約している（docs/07 §7.2）。

#### サーバーサイドのエラーメッセージ

| APIエンドポイント | エラー種別 | レスポンスメッセージ |
|-----------------|---------|------------------|
| `/api/contact` | バリデーションエラー | `すべての項目を入力してください` / `有効なメールアドレスを入力してください` / `メッセージは5000文字以内で入力してください` |
| `/api/contact` | メール送信失敗 | `メールの送信に失敗しました。しばらくしてからもう一度お試しください。` |
| `/api/contact` | サーバーエラー | `サーバーエラーが発生しました。しばらくしてからもう一度お試しください。` |
| `/api/portfolio` | データ取得失敗 | `ポートフォリオデータの取得に失敗しました` |

全エンドポイントのレスポンス形式は `{ error: string }` に統一済み（`src/types/api-error.ts` の `ApiErrorResponse`）。内部エラーメッセージ（`Error.message`）は返さない。

### 5.4 コンテンツセキュリティ

| 項目 | 現状 |
|------|------|
| XSS対策 | Reactの自動エスケープ機構により、ユーザー入力のHTMLインジェクションを防止 |
| 生HTMLの直接挿入 | 使用していない (ReactのJSXエスケープのみ) |
| ユーザー入力の表示 | コンタクトフォームの入力値はサーバーサイドでメール本文に埋め込まれるのみで、サイト上に表示されない |
| HTMLメールへの埋め込み | Reactのエスケープが効かない唯一の出力先。`escapeHtml()` による明示的な出力エスケープを実装済み (§8.1) |

## 7. 既知のセキュリティ考慮事項

### 7.1 現在のリスク評価

| リスク | 深刻度 | 説明 | 対策状況 |
|--------|-------|------|---------|
| コンタクトフォームのスパム | 中 | レート制限やCAPTCHAが未実装のため、bot等によるスパム送信のリスクがある | 未対策 |
| ポートフォリオAPIのエラー情報漏洩 | 低 | `/api/portfolio` のエラーレスポンスに内部エラーメッセージが含まれる | 一部対策 (contactは対策済み) |
| サーバーサイドバリデーションの不完全性 | 低 | クライアントサイドより緩いバリデーションルールが適用されている | 一部対策 |
| CSP (Content Security Policy) 未設定 | 低 | CSPヘッダーが設定されていないため、XSS攻撃への多層防御が不足 | 未対策 |
| レート制限 | 低 | API Routesにレート制限が未実装 | 未対策 |

### 7.2 推奨セキュリティ改善

#### 優先度: 高

| 改善項目 | 説明 | 実装方法 |
|---------|------|---------|
| スパム対策 | コンタクトフォームへのbot送信を防止 | Google reCAPTCHA v3 またはhCaptchaの導入、ハニーポットフィールドの追加 |
| レート制限 | API Routes への過剰リクエストを制限 | Cloud Run の max-instances 設定、または `upstash/ratelimit` ライブラリの導入 |
| サーバーサイドバリデーション強化 | クライアントサイドと同一のバリデーションルールを適用 | Zodスキーマをサーバーサイドでも共有利用 |

#### 優先度: 中

| 改善項目 | 説明 | 実装方法 |
|---------|------|---------|
| CSPヘッダー設定 | Content Security Policyの導入によるXSS多層防御 | `next.config.js` の `headers` 設定、またはmiddlewareでのヘッダー付与 |
| エラーレスポンス統一 | `/api/portfolio` のエラーレスポンスから内部詳細を除去 | 本番環境では汎用メッセージのみ返却するように条件分岐 |
| セキュリティヘッダー追加 | ブラウザのセキュリティ機能を活性化 | `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` の設定 |

#### 優先度: 低

| 改善項目 | 説明 | 実装方法 |
|---------|------|---------|
| Subresource Integrity (SRI) | 外部リソース (Google Fonts) の改ざん検知 | `next/font/google` への移行による外部リソース依存の排除 |

### 7.3 依存パッケージ監査（実装済み）

> 旧「優先度: 低」の改善項目だったが、issue #80 で実装済みへ移行した。

#### 仕組み

| 層 | 担当 | 内容 |
|---|---|---|
| **Dependabot** | `.github/dependabot.yml` | 更新 PR を能動的に作る（npm / github-actions、週次） |
| **CI（ブロッキング）** | `pnpm audit:ci` | 本番依存の **critical** のみで CI を落とす |
| **CI（可視化）** | `pnpm audit`（組み込み） | dev を含む全依存の全レベルをログに出す（`continue-on-error: true`） |
| **ローカル確認** | `pnpm audit:prod` | 本番依存のみを全レベルで確認する |

> **スクリプト名の注意**: `audit` は pnpm の**組み込みコマンド名**のため、`package.json` に
> `"audit": "..."` を定義しても `pnpm audit` では組み込みが実行され、スクリプトは無視される。
> そのため本番依存に絞るスクリプトは `audit:prod` という名前にしている。

GitHub 側の Dependabot alerts（Settings → Code security）も有効化する必要がある。

#### メジャー更新は自動 PR の対象外とする

判断が必要なメジャー更新は `.github/dependabot.yml` の `ignore` で除外し、**専用の issue で扱う**。

| 除外対象 | 理由 | 対応 issue |
|---|---|---|
| `next` | Node / ESLint の前提条件が絡む | #88 |
| `react` / `react-dom` / `@types/react` | `forwardRef` を多用する atoms 全体に影響する | #104 |
| `@types/node` | Node ランタイムのバージョン統一と揃える必要がある | docs/11 タスク #53 |

除外する理由は 2 つ。自動 PR には**何を確認すべきかが残らない**こと、そして**毎週再作成されて競合の温床になる**ことである。

実際に 2026-09-19、Dependabot の PR を続けてマージした際に `pnpm-lock.yaml` が破損し（同一マッピング内でキーが重複）、CI と Cloud Run デプロイが停止した。複数の PR が同じロックファイルを触るため、**テキストとしてはマージできるが YAML としては壊れる**という形で検知をすり抜けた。

各 issue の完了時に、対応する除外を `ignore` から外す。

#### なぜ閾値を「本番依存の critical」に置くか

**件数を 0 にすることが目的ではなく、自分の構成で発火するものを判定して潰すことが目的**である。

実測（2026-09-19 時点）:

| 範囲 | 件数 |
|---|---|
| 全依存 | 48 件（high 26 / moderate 20 / low 2 / critical 0） |
| **本番依存のみ（`--prod`）** | **11 件**（high 6 / moderate 4 / low 1 / critical 0） |

差分の 37 件は `eslint` / `vitest` / `testcontainers` / `jsdom` 等の **devDependency 経由**で、本番コンテナには含まれない。ここを含めて CI を落とすと、対処のしようがない指摘で全 PR がブロックされ、**監査そのものが形骸化する**。

本番依存の 11 件はすべて `@google-cloud/storage` と `next` 経由の間接依存であり、直接の更新では解消できない（`pnpm.overrides` か上流の更新待ちになる）。

#### 引き上げの段取り

本番依存の high 6 件（`postcss` / `nanoid` / `fast-xml-builder` / `form-data`）を解消できた段階で、`audit:ci` の閾値を `--audit-level high` に引き上げる。**閾値は据え置くのではなく、解消に応じて締めていく**。

#### 運用上の注意

アドバイザリは件名ではなく `patched_versions` で区別する。同名・類似タイトルのアドバイザリが複数存在し（例: Next.js の "Denial of Service with Server Components" は 4 件あり、修正版がそれぞれ異なる）、件名だけで「対応済み」と判断すると取りこぼす。

## 8. メール送信のセキュリティ

### 8.1 HTMLメールテンプレート（対策済み）

コンタクトフォームから受け取った `name`, `email`, `message` の値がHTMLメールテンプレートに埋め込まれる (`src/repositories/resend.ts`)。サイト本体と異なりReactのJSXエスケープが効かないため、本プロジェクトで**出力エスケープを明示的に行う唯一の箇所**である。

#### 実装

`src/lib/html-escape.ts` の `escapeHtml()` を通してから埋め込む。

| パート | エスケープ | 理由 |
|--------|-----------|------|
| `html` | する | メールクライアントがHTMLとして解釈するため。`&`, `<`, `>`, `"`, `'` を実体参照へ変換する |
| `text` | しない | text/plain はHTMLとして解釈されない。変換すると `&amp;` 等が読者にそのまま見える |
| `subject` | しない | メールヘッダーでありHTMLではない。エンコードはResend APIが担う |

`'` には `&apos;` ではなく数値参照 `&#39;` を割り当てる。`&apos;` はHTML4の実体参照に含まれず、古いメールクライアントで解決されない場合があるため。

5文字の置換は単一の正規表現とコールバックで一度に行う。個別の `replace` を重ねると `<` → `&lt;` の結果に含まれる `&` が再変換され `&amp;lt;` となる二重エスケープが起きるため。

#### 入力バリデーションとの関係

Zod (`ContactFormSchema`) による検証は「受け付けてよい値か」の判定であり、出力先の文法に合わせる処理ではない。`message` は自由記述 (10〜2000文字) を許可するため、**検証を通過した値にもHTMLタグは含まれ得る**。入力検証と出力エスケープは別レイヤの対策として両方必要である (`.claude/rules/security.md`「XSS: ユーザー入力のサニタイズ + CSPヘッダー設定 + 出力エスケープの多層防御」)。

#### 検証

| テスト | 対象 |
|--------|------|
| `src/lib/html-escape.test.ts` (UT) | `escapeHtml()` の変換仕様（16ケース） |
| `src/app/api/contact/route.integration.test.ts` (IT) | Resendへ送信される payload の `html` がエスケープ済み・`text` が生値であること（エスケープ呼び出し忘れの回帰検出） |

### 8.2 Reply-To ヘッダー

- 問い合わせ者のメールアドレスが `replyTo` ヘッダーに設定される
- これにより返信時に問い合わせ者に直接返信が可能
- 送信元 (`from`) はサイトのドメインメールアドレスで固定されており、なりすましの防止に寄与

### 9.2 データ保持方針

- コンタクトフォームの入力データはメール送信後にサーバー上に保持しない
- データベースやログファイルへの永続的な保存は行わない
- Resend APIのログにメール送信記録が残る可能性がある (Resendのデータ保持ポリシーに準拠)
