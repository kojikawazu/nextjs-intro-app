## 1. パフォーマンス要件

### 1.1 目標指標

| 指標 | 目標値 | 備考 |
|------|--------|------|
| 初回ページロード時間 | 3秒以内 | LTE回線環境を想定 |
| API レスポンス時間 | 500ms以内 | `/api/portfolio` エンドポイント |
| Time to Interactive (TTI) | 3.5秒以内 | モバイルデバイス基準 |
| Largest Contentful Paint (LCP) | 2.5秒以内 | Core Web Vitals基準 |
| First Input Delay (FID) | 100ms以内 | Core Web Vitals基準 |
| Cumulative Layout Shift (CLS) | 0.1以下 | Core Web Vitals基準 |

### 1.2 現在の実装

#### クライアントサイドレンダリング

- メインページ (`src/app/page.tsx`) は `'use client'` ディレクティブによるクライアントサイドレンダリング (CSR) で動作
- 初回ロード時に `/api/portfolio` エンドポイントからデータを fetch し、ローディングスピナーを表示
- データ取得完了後にコンテンツを描画するため、初回表示までに API レスポンス待ちが発生する

#### APIキャッシュ戦略

```text
Cache-Control: public, s-maxage=300, stale-while-revalidate=86400
```

| パラメータ | 値 | 説明 |
|------------|------|------|
| `s-maxage` | 300秒 (5分) | CDNエッジキャッシュの有効期間 |
| `stale-while-revalidate` | 86400秒 (24時間) | キャッシュ期限後もstaleレスポンスを返しつつバックグラウンドで再検証する期間 |
| `public` | - | CDNおよび共有キャッシュでキャッシュ可能 |

この設定により、CDN やリバースプロキシ上でポートフォリオデータのレスポンスがキャッシュされ、5分間は同一レスポンスが即座に返却される。5分経過後も24時間以内であればstaleレスポンスを返しつつ裏で再取得が行われるため、ユーザー体感としてはほぼ常にキャッシュヒットとなる。（Cloud Run 環境では CDN を前段に配置することで効果を発揮する）

#### 画像最適化

- Next.js `Image` コンポーネントを使用 (`next/image`)
- ヒーロー画像には `priority` 属性を付与し、プリロードを実施
- `next.config.js` にて `images.unoptimized: true` が設定されており、Next.js組み込みの画像最適化 (WebP変換、リサイズ等) は無効化されている
- 画像の最適化は外部ソース (GCS上の画像) に依存

#### フォント読み込み

- Google Fonts (`Zen Old Mincho`, `Zen Kaku Gothic New`) を CSS `@import` で読み込み
- `@import` による読み込みはレンダリングブロッキングが発生する可能性がある。`layout.tsx` の `<head>` に `preconnect` を置き、接続確立を前倒ししている
- `display=swap` パラメータにより、フォント読み込み完了までシステムフォントでフォールバック表示
- **`next/font` は使わない。** 日本語のサブセット指定ができず全字形を取りに行くため、日本語サイトではかえって重くなる。Google Fonts の CSS は unicode-range で字形を分割配信するので、実際に使う範囲だけが落ちてくる
- 等幅（期間・件数・SNS 名）はシステムフォントを使い、追加のダウンロードを発生させない

#### バンドル最適化

- webpack設定により、Node.jsモジュール (`fs`, `net`, `tls`, `crypto`, `stream`, `url`, `zlib`, `http`, `https`, `assert`, `os`, `path`, `child_process`) をクライアントサイドバンドルから除外
- サーバーサイド専用ライブラリ (`@google-cloud/storage`, `resend`) がクライアントバンドルに含まれることを防止

### 1.3 パフォーマンス改善の推奨事項

| 項目 | 現状 | 推奨 |
|------|------|------|
| 画像最適化 | `unoptimized: true` | Next.js Image Optimization の有効化（Cloud Run 環境では外部画像最適化サービスの利用を検討） |
| フォント読み込み | CSS `@import` | `next/font/google` の利用によるセルフホスティングとプリロード |
| レンダリング方式 | CSR | SSR/SSG の検討によるFCP改善 |
| CSSアニメーション | 多数のアニメーション定義 | `prefers-reduced-motion` メディアクエリへの対応 |

## 2. スケーラビリティ

### 2.1 アーキテクチャ概要

本プロジェクトはシングルページアプリケーション (SPA) として構築されており、Google Cloud Run 上に Docker コンテナとしてデプロイされる。

| レイヤー | テクノロジー | スケーリング方式 |
|----------|-------------|----------------|
| フロントエンド + API | Next.js 14 (App Router) on Cloud Run | Cloud Run のオートスケーリング（リクエスト数に応じたインスタンス増減） |
| データストレージ | Google Cloud Storage (GCS) | GCSマネージドサービスによる自動スケーリング |
| メール送信 | Resend API | Resend SaaS による自動スケーリング |

### 2.2 スケーラビリティ特性

- **静的資産**: Cloud Run コンテナから直接配信（CDN を前段に配置することでグローバル配信が可能）
- **APIリクエスト**: Serverless Functionsとして実行されるため、同時リクエスト数に応じて自動的にインスタンスが増減する
- **データ取得**: GCSからのデータ取得はAPIキャッシュ (`s-maxage=300`) により、GCSへの直接アクセス頻度を大幅に抑制している
- **コンタクトフォーム**: Resend APIを介したメール送信はステートレスな処理であり、スケーリングの制約とならない

### 2.3 想定トラフィック

| 指標 | 想定値 | 備考 |
|------|--------|------|
| 月間ページビュー | 10,000PV以下 | 個人ポートフォリオサイトとしての想定 |
| 同時接続数 | 50以下 | 通常時の想定 |
| コンタクトフォーム送信 | 月100件以下 | メール送信API呼び出し |

**レートリミット**: `POST /api/contact` はクライアント IP あたり 10分 / 5回に制限している（docs/06 §10）。想定トラフィック（月100件以下）に対して十分な余裕があり、正当な利用者が引っかかることは想定していない。ただし履歴はプロセス内メモリに持つため、Cloud Run が水平スケールすると実効上限は「5回 × 稼働インスタンス数」になる。

## 3. 可用性・信頼性

### 3.1 可用性目標

| 指標 | 目標値 | 備考 |
|------|--------|------|
| 稼働率 | 99.9% | Cloud Run プラットフォームの SLA 準拠 |
| 計画停止 | なし | Cloud Run のローリングアップデートによりゼロダウンタイムデプロイが可能 |

### 3.2 障害対応

#### データ取得の耐障害性

- 開発環境ではGCS障害時にローカルの `sample.json` にフォールバックするロジックが存在する (`src/repositories/portfolio.ts`)。ただし `sample.json` はリポジトリに含まれていないため、手動で配置しない限りフォールバックは成立しない
- 本番環境ではGCS障害時に HTTP 500 エラーレスポンスを返却
- CDNキャッシュ (`stale-while-revalidate=86400`) により、GCS障害発生後も最大24時間はstaleデータを返却可能

#### メール送信の耐障害性

- Resend API障害時はユーザーにエラーメッセージを表示
- エラーメッセージは内部情報を漏洩しないよう汎用的なメッセージを返却
- 開発環境のみ `console.error` で詳細ログを出力

#### クライアントサイドのエラーハンドリング

- ポートフォリオデータの取得失敗時はエラー画面とリロードボタンを表示
- コンタクトフォーム送信失敗時はエラーメッセージをフォーム内に表示し、再送信を促す

### 3.3 デプロイ戦略

- Cloud Run のローリングアップデートによるゼロダウンタイムデプロイ
- GitHub リポジトリの main ブランチへのプッシュにより GitHub Actions 経由で自動デプロイ（`.github/workflows/deploy_to_googlecloud.yml`）
- Docker イメージを Artifact Registry にプッシュ後、Cloud Run にデプロイ

### 4.4 クローラ向けファイル

App Router の規約ルート（`src/app/sitemap.ts` / `src/app/robots.ts`）で生成する。いずれも基準オリジンに
`src/lib/site-url.ts` の `getSiteUrl()` を使用し、ドメイン文字列を 1 箇所に集約している。

| 生成物 | 生成元 | 内容 |
|---|---|---|
| `/sitemap.xml` | `src/app/sitemap.ts` | トップページ 1 件（`changefreq: monthly` / `priority: 1`）。各セクションはアンカーのため独立した URL を持たない |
| `/robots.txt` | `src/app/robots.ts` | 全クローラに全ページを許可。`Host`（正規ホスト）と `Sitemap` を明示 |

出力例:

```text
User-Agent: *
Allow: /

Host: introtechkkplus.com
Sitemap: https://introtechkkplus.com/sitemap.xml
```

> **静的生成である点に注意**: `sitemap.ts` / `robots.ts` はビルド時に評価され静的ファイルとして出力される
> （`next build` のルート一覧で `○ (Static)`）。したがって Cloud Run の**実行時**環境変数 `SITE_URL` では内容が変わらない。
> 出力を変えたい場合はビルド時に `SITE_URL` を渡す必要がある。既定では正規オリジンが焼き込まれるため、本番では追加設定が不要。

## 5. アクセシビリティ仕様

### 5.1 準拠基準

WCAG 2.1 Level AA を目標基準として実装する。

### 5.2 現在の実装

#### ARIA属性

| コンポーネント | ARIA属性 | 設定値 |
|----------------|----------|--------|
| モバイルメニューボタン (`Header`) | `aria-label` / `aria-expanded` | `メニューを開く` / 開閉状態を反映 |
| テーマトグル (`ThemeToggle`) | `role="group"` + `aria-label` | `配色テーマ`。各ボタンは `ライトテーマに切り替える` / `ダークテーマに切り替える`、記号 (○ / ●) は `aria-hidden="true"` |
| SNSリンク (`SocialLinks`) | `aria-label` | `{SNS名}のプロフィールを開く` |
| 入力欄 (`Input` / `TextArea`) | `aria-invalid` / `aria-describedby` | エラー時に `true` / エラーまたはヒントの id（同時には指さない） |
| 送信完了 (`ContactForm`) | `role="status"` + `aria-live="polite"` | フォームと差し替わるため polite |
| 送信エラー (`ContactForm`) | `role="alert"` | 利用者の対応を要するため assertive 相当 |
| ローディングスピナー (`Button`) | `aria-hidden="true"` | 状態は `disabled` 属性が伝えるため、装飾を読み上げさせない |

#### キーボードアクセシビリティ

- **フォーカスインジケーター**: `Button` に `focus-visible:ring-2 focus-visible:ring-acc focus-visible:ring-offset-2 focus-visible:ring-offset-paper` を適用。`primary` バリアントは地が `--acc` で塗られているため、オフセットが無いとリングが同化する
- **操作部品**: `Header` のナビ / メニューボタン、`SocialLinks`、`ThemeToggle`（`ring-inset`）も `focus-visible:ring-2 focus-visible:ring-acc`
- **フォーム要素**: `Input`, `TextArea` は `focus:ring-2 focus:ring-acc`（エラー時は `focus:ring-warn`）。`focus-visible` ではなく `focus` を使う理由は §7.2
- **ナビゲーションボタン**: `<button>` 要素を使用しており、キーボード操作 (Tab/Enter/Space) に対応
- **スムーススクロール**: CSS `scroll-behavior: smooth` により、ページ内リンクのスクロールがスムーズに動作

#### フォームアクセシビリティ

- **必須フィールド表示**: 必須項目にアクセント色のアスタリスク (`*`) を表示 (`<span className="ml-1 text-acc">*</span>`)
- **ラベルの関連付け**: `useId()` で生成した id を `htmlFor` / `id` で結ぶ（呼び出し側が `id` を指定した場合はそちらを優先）。ラベルを描画していることと関連付けていることは別で、関連付けが無いとクリックでフォーカスが移らず読み上げも対応を伝えない
- **エラーメッセージ**: フォーム要素直下に `--warn` のテキストで表示し、枠線も `--warn` に変える
- **ローディング状態**: 送信中はボタンが `disabled` となり、スピナーアニメーションを表示
- **`<label>` 要素**: 各フォーム入力に `htmlFor` / `id` で関連付けたラベルを配置。ラベルのクリックでフォーカスが移り、スクリーンリーダーも対応を読み上げる。id は呼び出し側指定が無ければ `useId()` で生成する
- **エラーの関連付け**: `aria-describedby` でエラー文・補助説明を入力欄に紐付け、エラー時は `aria-invalid` を付与
- **送信結果の通知**: 完了画面は `role="status"`、送信エラーは `role="alert"` で支援技術へ通知

#### 色コントラスト

- 地 (`--paper`) に対する文字色はすべてトークンで定義し、固定色を直接書かない
- エラー状態は `text-warn` / `border-warn` により視覚的に区別する（ライト 5.52:1 / ダーク 7.52:1）

配色トークン (issue #136) は、以下の実測値で WCAG 2.1 AA を満たす。**この表は `src/app/design-tokens.test.ts` が機械的に検証している。** 色を少し調整しただけで基準を割り込むが、その差は人の目では判別できないため、コメントではなくテストで固定している。

| トークン | 用途 | ライト | ダーク | 必要値 |
|----------|------|--------|--------|--------|
| `--ink` | 見出し・強調 | 16.69:1 | 15.78:1 | 4.5:1 |
| `--body` | 本文 | 12.38:1 | 12.12:1 | 4.5:1 |
| `--lead` | リード文 | 11.30:1 | 12.98:1 | 4.5:1 |
| `--mute` | 補助・ラベル | 5.41:1 | 6.35:1 | 4.5:1 |
| `--acc` | アクセント文字 | 7.02:1 | 8.07:1 | 4.5:1 |
| `--warn` | 注意表示 | 5.52:1 | 7.52:1 | 4.5:1 |
| `--acc-on` (対 `--acc`) | アクセント上の文字 | 7.02:1 | 8.07:1 | 4.5:1 |
| `--field` | 操作部品の境界 | 3.31:1 | 3.41:1 | 3:1 |

いずれも背景 `--paper` に対する値 (`--acc-on` のみ `--acc` に対する値)。

**`--rule` と `--field` を分けている理由。** WCAG 1.4.11 (非テキストのコントラスト) は「UI 部品の境界」に 3:1 を要求するが、純粋に装飾的な区切り線は対象外。セクション区切りの細い罫線に 3:1 を課すと線が太く重くなり、書類としての繊細さが失われる。そのため役割で 2 つに分けている。

| トークン | 役割 | コントラスト要件 |
|----------|------|------------------|
| `--rule` | 装飾的な区切り線 | なし (対象外) |
| `--field` | 入力欄・トグルなど操作できる部品の境界 | 3:1 以上 |

`--rule` を文字色や操作部品の境界に流用すると基準を割るため、テストで「`--rule` が文字色として使える水準に達していないこと」も併せて検証している (誤用の検出)。

### 7.2 使用CSS機能の互換性

| CSS機能 | 使用箇所 | 互換性リスク |
|---------|---------|------------|
| CSS Custom Properties | 配色トークン (`--paper` / `--ink` 等)。`tailwind.config.js` の色はすべて `var(--*)` を指す | 主要ブラウザで対応済み |
| `oklch()` | アクセント色 `--acc` (`oklch(0.45 0.09 255)` / ダークは `oklch(0.74 0.11 255)`) | Safari 15.4 / Chrome 111 / Firefox 113 以降。**フォールバックを置いていない**。カスタムプロパティ自体はどのブラウザでも解析できるが、`var(--acc)` を参照した側が**計算値の時点で無効**になり、継承プロパティ (`color`) は継承値、非継承プロパティ (`background-color` / `border-color`) は初期値 (`transparent` / `currentColor`) に化ける |
| CSS Grid | About レイアウト、Hero の数値帯、`CareerCard` の技術スタック (`dl`) | 主要ブラウザで対応済み |
| `scroll-behavior: smooth` | ページ内ナビゲーション | 主要ブラウザで対応済み |
| `focus-visible` | Button, Header, SocialLinks, ThemeToggle | 主要ブラウザで対応済み |
| `focus` (擬似クラス) | Input, TextArea | 入力欄は `focus-visible` ではなく `focus` を使う。`focus-visible` はブラウザが「キーボード操作らしい」と判断したときだけリングを出すため、クリックでフォーカスした入力欄にリングが出ない。どこに入力しているかは操作手段によらず示す必要がある |
| `prefers-color-scheme` | 配色トークンの既定値 (OS 設定への追従) | 主要ブラウザで対応済み |
| CSS Animations / Keyframes | `fade-in-up` (Hero の初回表示のみ) | 主要ブラウザで対応済み |

> **`light-dark()` は使っていない。** 1 行で書けるが、未対応ブラウザではカスタムプロパティが
> **計算値の時点で無効**になり、`var()` を参照した側のプロパティごと落ちる。閲覧環境を選べない
> 相手に出す画面では危険なため、`--light-*` / `--dark-*` を定義して 4 ブロックで写像する方式を採った
> （`globals.css`）。
>
> **旧デザインで使っていた `backdrop-filter: blur()`（`glass-effect` / `glass-card`）と
> `mask-composite: exclude`（`gradient-border`）は、issue #138 でクラスごと廃止した。**
