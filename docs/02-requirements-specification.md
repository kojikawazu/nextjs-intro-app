## 1. 機能要件一覧

> **要件は「何を満たすか」で書き、実装手段（装飾・アニメーションの種類など）を要件にしない**（issue #149 / #169）。
> かつて本章は旧デザインの実装をそのまま要件として書いており、デザインを刷新するたびに実装と食い違った。
> 掲載内容に関わる要件は**掲載データ（GCS の JSON）と実装を正**として記述する。
>
> **ID は再利用しない。** 廃止した要件の ID は欠番とし、各節の注記に理由を残す。

## 2. 主要機能の受入基準

### 2.1 お問い合わせフォーム（FR-CONTACT）

| # | 受入基準 | 確認方法 |
|---|----------|----------|
| AC-1 | 名前が空欄の場合、「お名前は必須です」のエラーメッセージが表示されること | フォーム送信テスト |
| AC-2 | 名前が1文字の場合、「お名前は2文字以上で入力してください」のエラーメッセージが表示されること | 境界値テスト |
| AC-3 | 名前が51文字以上の場合、「お名前は50文字以内で入力してください」のエラーメッセージが表示されること | 境界値テスト |
| AC-4 | 不正なメールアドレス形式の場合、「正しいメールアドレスを入力してください」のエラーメッセージが表示されること | 形式チェックテスト |
| AC-5 | メッセージが9文字以下の場合、「お問い合わせ内容は10文字以上で入力してください」のエラーメッセージが表示されること | 境界値テスト |
| AC-6 | メッセージが2,001文字以上の場合、「お問い合わせ内容は2000文字以内で入力してください」のエラーメッセージが表示されること | 境界値テスト |
| AC-7 | 全項目が正しく入力された状態で送信ボタンを押すと、送信中状態（ローディングスピナー+「送信中...」テキスト）が表示されること | 動作確認 |
| AC-8 | メール送信成功後、完了画面（「送信完了」の見出しと完了メッセージ）が表示されること | E2Eテスト |
| AC-9 | メール送信失敗時、API が返したエラーメッセージが `role="alert"` で表示されること | APIモックテスト |
| AC-10 | 完了画面の「新しいお問い合わせ」ボタンを押すと、フォームが初期状態にリセットされること | 動作確認 |
| AC-11 | フォームを経由しない直接リクエストでも、FR-CONTACT-003〜005 の制約（例: 2,001 文字以上のメッセージ）に反する入力が 400 で拒否されること | APIテスト |
| AC-12 | 送信されたメールのReply-Toに送信者のメールアドレスが設定されていること | メール受信確認 |
| AC-13 | 同じ送信元から 10 分間に 6 回目の送信が 429 と `Retry-After` で拒否されること | APIテスト |

### 2.2 ポートフォリオデータ取得（FR-DATA）

| # | 受入基準 | 確認方法 |
|---|----------|----------|
| AC-1 | 本番環境でGCSからJSONデータを正常に取得できること | デプロイ後の動作確認 |
| AC-2 | 開発環境でsample.jsonからデータが読み込まれること | ローカル開発で確認 |

## 3. 非機能要件サマリー

非機能要件の詳細は `04-non-functional-specification.md` を参照のこと。以下に概要を記載する。

### 3.1 パフォーマンス

| 項目 | 要件 |
|------|------|
| ページ読み込み速度 | PageSpeed Insights Performance スコア 90点以上 |
| API応答時間 | ポートフォリオデータ取得API 500ms以内（キャッシュ利用時） |
| キャッシュ戦略 | s-maxage=300秒、stale-while-revalidate=86400秒 |
| 画像最適化 | Next.js Imageコンポーネントによる自動最適化、priority属性の適切な設定 |

### 3.2 セキュリティ

| 項目 | 要件 |
|------|------|
| 入力バリデーション | クライアントとサーバーで同じ Zod スキーマ（`ContactFormSchema`）による二重バリデーション |
| 環境変数管理 | APIキー、メールアドレス等の機密情報は環境変数で管理し、クライアントに露出しない |
| 外部リンク | SNSリンクにrel="noopener noreferrer"を付与 |
| エラーログ | 詳細なエラー情報をクライアントに返さない（統一形式 `{ error: string }`）。エラーは本番でもサーバー側のログに残す |
| レートリミット | `POST /api/contact` は送信元ごとに 10 分間 5 回まで（FR-CONTACT-012） |
| XSS 対策 | nonce ベースの CSP、問い合わせメール HTML の出力エスケープ（docs/06） |
| GCSバケット | プライベートバケットを使用、サービスアカウント認証による安全なアクセス |

### 3.3 可用性・信頼性

| 項目 | 要件 |
|------|------|
| 稼働率 | 99.9%以上（Cloud Run プラットフォームに依存） |
| エラーハンドリング | データ取得失敗時のフォールバック、ユーザー向けエラーメッセージ、リロード導線 |
| グレースフルデグラデーション | GCS障害時でも開発環境ではローカルデータで動作継続 |

### 3.4 保守性

| 項目 | 要件 |
|------|------|
| コンポーネント設計 | Atomic Design（Atoms/Molecules/Organisms）による階層的コンポーネント構造 |
| 型安全性 | TypeScriptによる完全な型定義（PortfolioData型を起点とした型階層） |
| コード品質 | ESLint + Prettier + TypeScript strict mode による静的解析 |
| データとUIの分離 | ポートフォリオデータはJSON外部化し、UIコードとコンテンツを分離 |

### 3.5 レスポンシブデザイン

| 項目 | 要件 |
|------|------|
| ブレークポイント | Tailwind CSS標準（sm:640px, md:768px, lg:1024px, xl:1280px） |
| モバイル対応 | 全セクションがモバイル画面で正常に表示・操作可能であること |
| タッチ操作 | モバイルメニュー、ボタン、リンクがタッチ操作に対応していること |
