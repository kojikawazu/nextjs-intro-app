# セキュリティ

## 認証・認可

- 認証方式はプロジェクト要件に応じて選択する（JWT / セッション / Supabase Auth 等）。
- API エンドポイントごとにアクセス制御を設定する（公開 / 認証必須 / ロールベース）。

## 通信・アクセス制御

- 全通信は **HTTPS** を必須とする。
- **CORS** は許可するオリジンを明示的に指定する（`*` は本番で使用しない）。
  - **適用範囲**: 他オリジンから呼ばれる API を持つ場合のみ。**同一オリジン専用の API には適用しない。**
    CORS ヘッダーは「他オリジンからの読み取りを許可する」仕組みであり、付けないことが最も厳しい状態になる。
    ブラウザは既定で他オリジンからのレスポンス読み取りを拒否するため、同一オリジン専用 API に
    `Access-Control-Allow-Origin` を足すのは緩和にしかならない。
- **レートリミット** を導入する（認証系エンドポイントは特に厳しく制限）。
  - 認証を持たず 1 回の成功が外部リソースを消費するエンドポイント（メール送信・外部 API 呼び出し等）も
    同様に厳しく制限する。
  - 実装方式は規模に応じて選ぶ。水平スケールする実行環境でプロセス内カウンタを使う場合は
    「インスタンスごとの制限」になる限界を docs に明記すること。

## インジェクション対策

- **SQL インジェクション**: ORM またはパラメータバインドを必須とする。生 SQL の文字列結合は禁止。
- **XSS**: ユーザー入力のサニタイズ + CSP ヘッダー設定 + 出力エスケープの多層防御。
  - CSP は `script-src` を nonce（+ `strict-dynamic`）で絞ること。`'unsafe-inline'` を許した
    `script-src` は XSS 対策として機能しないため、設定した扱いにしない。
- **CSRF**: セッション認証の場合は CSRF トークン必須。Bearer Token 認証（Cookie に保存しない場合）は不要。

## シークレット管理

- ローカル環境: `.env`（`.gitignore` に追加必須）
- 本番環境: Secret Manager 等のマネージドサービスを使用
